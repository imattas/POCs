# Corsair iCUE Update Service — Local Privilege Escalation to SYSTEM (iCUE2SYSTEM)

## Executive Summary

Mallory, an ordinary local Windows user, can route controlled package operations through her own medium-integrity `iCUE.exe` and cause Corsair's LocalSystem update service to execute a fixed proof command as `NT AUTHORITY\SYSTEM`. She does not need an administrator token, approve UAC, modify the installed iCUE package registry, or inject into another user's or elevated process. iCUE must already have been installed by an administrator or OEM.

The reproduced PoC uses the service's path-based acceptance of `iCUE.exe`, changes the package root to `%TEMP%\iCUE2SYSTEM`, adds one `codex-probe` action to a private copy of `cuepkg.registry`, and asks SYSTEM-owned `cuepkg.exe` to run:

```text
cmd.exe /d /c C:\Windows\System32\whoami.exe /all
```

The resulting file identified `NT AUTHORITY\SYSTEM`, SID `S-1-5-18`, and System Mandatory Level. The PoC does not provide a shell or arbitrary command interface.

| Attribute | Verified value |
|-----------|----------------|
| Product | Corsair iCUE 5 Software |
| Assessed release | 5.52.93 |
| Service binary | `iCUEUpdateService.exe` 5.52.93.0 |
| Attack position | Standard local user |
| Demonstrated impact | Fixed command execution as LocalSystem |
| Administrator required during exploitation | No |

I reviewed the exact signed binaries and the PoC, built and ran the reproducer locally on 2026-10-29, and observed the SYSTEM identity output. Corsair's proprietary source and release history were unavailable. Only iCUE 5.52.93 was assessed; the affected and fixed version ranges are unknown.

## Background

The assessed installation registered `iCUEUpdateService` as a manually started LocalSystem service. It exposed the Qt Remote Objects endpoint `local:Corsair_iCUE_Update_Service` over the named pipe `\\.\pipe\Corsair_iCUE_Update_Service`.

The service attempts to restrict clients by obtaining the pipe client's PID, resolving that process's executable path, and accepting a client whose path is beneath the iCUE product directory. That check distinguishes an obvious unrelated process from `iCUE.exe`, but it does not establish that code executing inside the accepted user-owned process is trusted.

The complete tested prerequisites were:

- iCUE 5.52.93 and `iCUEUpdateService` were already installed;
- Mallory could run ordinary code at medium integrity;
- Mallory could start her own iCUE process; and
- the installed service and protocol matched `iCUEUpdateService.exe` 5.52.93.0.

The PoC is one C++ DLL source plus a batch launcher. It uses only Windows and Windows SDK APIs and requires no Qt runtime, Qt SDK, or third-party runtime.

## Vulnerability Details

### Bug 1: Path-based client acceptance trusts a user-controlled process

The service accepts requests originating from the expected iCUE executable path. Mallory cannot normally overwrite that protected executable, but she can load code into her own medium-integrity `iCUE.exe`. The service then observes the approved Corsair path while processing requests generated by Mallory's code.

The PoC narrows this behavior rather than attaching broadly: it self-starts the current user's iCUE when needed and rejects cross-user, elevated, and non-product-path targets before injecting its own DLL.

**Expected:** The broker should authenticate the caller's token and authorize each privileged operation. An executable path is not a security identity for code running in a user-owned process.

### Bug 2: `setInstallDir()` accepts a user-controlled package root

Once connected, the client can select `%TEMP%\iCUE2SYSTEM` with `setInstallDir()`. The privileged package manager subsequently treats that user-writable directory as its package root.

The PoC copies the installed `cuepkg.registry` into this private directory and modifies only the copy. The installed registry remained byte-identical after the reproduced run, with SHA-256:

```text
9F40A548352EC1E3CC34088D34D03631C3B968A59C5BEB5E3D1B2DB8E5427CC3
```

**Expected:** A privileged package manager should load authenticated metadata only from a fixed SYSTEM- or Administrators-owned location.

### Bug 3: Controlled registry actions reach a LocalSystem execution sink

The private registry declares one installed package named `codex-probe`. Its sole `run-executable` action points to the private copy of `cmd.exe` and supplies fixed arguments that run `C:\Windows\System32\whoami.exe /all` and redirect the result to `%TEMP%\iCUE2SYSTEM\whoami.txt`.

The PoC resolves the `setInstallDir`, `runActions`, and `startOperation` Qt Remote Objects method indices dynamically from the service metadata. It does not assume build-specific method numbers. It then uses the operation ID returned by `runActions()` when invoking `startOperation()`.

### Dynamic protocol behavior

The DLL implements the required Qt Remote Objects wire subset directly over the named pipe; it does not link against Qt. At runtime it:

- reads the service's dynamic metadata and resolves methods by their exact signatures rather than fixed numeric indexes;
- rejects missing or duplicate required signatures;
- uses the operation ID returned by `runActions()` when constructing the later `startOperation()` request;
- validates packet IDs, lengths, string encodings, variant types, reply serials, and required response names; and
- handles partial named-pipe reads and writes until each complete packet has been transferred.

This reduces dependence on method ordering, but it is not a claim of universal version compatibility. The service's surrounding authorization, schema, and package-manager behavior still require independent testing on each release.

The observed attack flow was:

```text
Standard user (no admin token, no UAC)
  │
  ├─► rundll32 loads poc.dll and calls Run
  ├─► PoC starts or finds the current user's medium-integrity iCUE.exe
  ├─► PoC validates same user, same session, non-elevated target, and protected product path
  ├─► PoC loads itself into that iCUE.exe
  │
  └─► iCUE-hosted worker
        ├─► copies cuepkg.registry and cmd.exe to %TEMP%\iCUE2SYSTEM
        ├─► inserts the fixed codex-probe action into the private registry
        ├─► starts iCUEUpdateService if necessary
        ├─► connects to local:Corsair_iCUE_Update_Service
        ├─► setInstallDir(%TEMP%\iCUE2SYSTEM)
        ├─► runActions("install", ["codex-probe"])
        ├─► startOperation(returned operation ID)
        └─► LocalSystem cuepkg.exe runs the fixed whoami command
              └─► %TEMP%\iCUE2SYSTEM\whoami.txt
```

**Expected:** Executable actions derived from user-writable or unauthenticated package metadata should be rejected before any privileged child starts.

The exact product source was unavailable, so these details are grounded in the assessed binaries, the protocol implemented by the PoC, and the reproduced runtime result rather than claimed as original vendor source.

## Exploitability Analysis

The demonstrated primitive is fixed command execution as LocalSystem from a standard-user starting position. The reproduced output contained these identity facts:

```text
User Name:  NT AUTHORITY\SYSTEM
SID:        S-1-5-18
Integrity:  System Mandatory Level
```

Three controls narrow the conclusion:

- the PoC accepts only the current user's non-elevated iCUE process beneath the protected Corsair product directory;
- it modifies a private registry copy while the installed registry hash remains unchanged; and
- it supplies only the fixed `whoami.exe /all` proof command and exposes no command parameter or interactive shell.

The generated process runs in Session 0, which is expected for service-launched code. A visible command prompt is neither produced nor needed to demonstrate the privilege boundary crossing.

The PoC restores the original package root and the prior service state. It removes the private `cuepkg.registry` and copied `cmd.exe`, leaving only `whoami.txt`. This limits the reproduction's persistent effect while preserving independently inspectable proof.

A separate runtime matrix across earlier or later iCUE releases was not performed. No claim is made about versions other than 5.52.93, a first affected release, a fixed release, prevalence, or vendor remediation status.

## Proof of Concept

### Files

| File | Purpose |
|------|---------|
| [`poc.cpp`](./poc.cpp) | Windows-SDK-only DLL source: validates and starts iCUE, self-injects, prepares the private registry, speaks the QtRO protocol, restores state, and cleans private inputs |
| [`run.bat`](./run.bat) | Finds the x64 MSVC toolchain, builds `poc.dll`, removes compiler intermediates, runs the exported function, and prints the proof |
| [`WRITEUP.md`](./WRITEUP.md) | Technical report and reproduction instructions |

The regression harness is not shipped with the three-file source package.

### Build

`run.bat` builds the DLL automatically from an ordinary Command Prompt. Microsoft Visual Studio Build Tools with the C++ and Windows SDK components must already be installed; Qt and third-party SDKs are not required.

The equivalent manual command from a Visual Studio x64 Native Tools prompt is:

```bat
cl /nologo /LD /std:c++17 /EHsc /O2 /DUNICODE /D_UNICODE poc.cpp /link Advapi32.lib winsqlite3.lib /OUT:poc.dll
```

The successful build was inspected with `dumpbin /dependents`. Its imported DLLs were limited to:

```text
ADVAPI32.dll
winsqlite3.dll
KERNEL32.dll
```

### Run

Use only on an authorized local test machine with iCUE 5.52.93 already installed:

```bat
run.bat
```

`run.bat` clears any stale proof, selects the latest installed x64 MSVC toolchain, executes the build command above, removes `poc.obj`, `poc.lib`, and `poc.exp`, then runs:

```bat
rundll32.exe "%~dp0poc.dll",Run
```

The resulting `poc.dll` remains beside the three source-package files for inspection or repeat execution. Every invocation rebuilds it from `poc.cpp`.

On the reproduced test, the output file reported `NT AUTHORITY\SYSTEM`, SID `S-1-5-18`, and System Mandatory Level. Inspect it directly with:

```bat
type "%TEMP%\iCUE2SYSTEM\whoami.txt"
```

The runtime leaves only that proof file. After preserving the result, remove it with:

```bat
rmdir /s /q "%TEMP%\iCUE2SYSTEM"
```

This PoC changes privileges on the local test system. It should not be run outside an explicitly authorized lab.

## Remediation

1. **Authenticate the caller token.** Do not authorize a client from an executable-path prefix. Bind each privileged request to the connecting user's token, integrity level, session, and permitted operation.

2. **Reduce endpoint and service permissions.** Grant pipe and service-control rights only to principals that require them. Treat ACL tightening as defense in depth, not a replacement for method authorization.

3. **Remove the caller-selected package root.** Remove `setInstallDir()` from the unprivileged interface or constrain it to a fixed, canonical SYSTEM- or Administrators-owned directory.

4. **Authenticate package metadata.** Verify the registry's owner, DACL, integrity, and cryptographic authenticity before consuming any action.

5. **Constrain executable actions.** Reject reparse-point traversal, require canonical targets below a trusted non-user-writable root, and verify an allowlisted signer or content hash immediately before launch.

6. **Bind validation to execution.** Keep the authorized install root, registry identity, package, operation ID, and executable action in one server-side decision so none can be substituted after validation.

7. **Add regression tests.** Cover a user-controlled legitimate iCUE process, an unrelated client, a cross-user client, an elevated client, a user-writable root, a modified registry, reparse points, and an unsigned executable action. No privileged child should start for the negative cases.

No vendor patch or fixed build was available for inspection. These are proposed remediation requirements, not a description of shipped changes.

## Summary

On the single assessed release, iCUE 5.52.93, a standard user could run one self-contained Windows-SDK-only DLL through `rundll32`, place controlled metadata in `%TEMP%`, and use the accepted iCUE update-service path to produce a `whoami /all` result as `NT AUTHORITY\SYSTEM`. The PoC required no administrator token or UAC approval after iCUE installation, restored the package root and service state, preserved the installed registry hash, and retained only `whoami.txt`.

The exact validated target was `iCUEUpdateService.exe` 5.52.93.0. Corsair source and release history were unavailable; affected-version boundaries and a fixed release remain unknown. The next useful validation is to run the same fixed-command regression test against a vendor-supplied corrected build.
